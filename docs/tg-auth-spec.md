# ТЗ: вариант C — Telegram как основная идентичность, подписка через Tribute

Статус: **черновик, не начато**. Рабочий документ для реализации;
ничего из описанного ниже ещё не сделано, кроме раздела 1 (уже есть).
Охват: вход/подписка (§2–7), Roblox после релиза (§7a), хранение
данных (§7b), права владельца (§7c).

## 0. Принципы

1. **Источник правды по подписке — только БД `apps/server`.**
   Tribute → подписанный webhook → `payments`/`subscriptions`. Бот и
   лаунчер подписку только *читают через сервер*. Лаунчер никогда не
   спрашивает бота напрямую: ответ бота/клиента подделывается, JWT +
   серверная проверка — нет.
2. **Telegram-аккаунт = основной логин** для стримеров. Email/пароль —
   legacy (старые аккаунты, админы, publish-CLI).
3. **TikTok — привязка, не логин-идентичность по умолчанию**: QR в
   приложении TikTok через встроенное окно входа (cookie-проверка
   сервером). Вход через TikTok остаётся как дополнительный способ.
4. **Секреты только на сервере**: ключ стримера для relay регистрирует
   сервер (бывший вариант A входит в C), `relay_admin_secret` уходит из
   лаунчера.
5. Любой «вход по ссылке/QR» подтверждается в боте явно (анти-фишинг).

## 2. Найденные проблемы в текущем коде

- **B1 (баг).** Бот `bind()` читает `data.payment_url` и
  `data.email_masked`, а `/api/tg/bind` отдаёт `product_url` и
  `email_masked` не отдаёт → после привязки бот никогда не показывает
  ссылку оплаты и пишет «ваш аккаунт».
- **B2 (безопасность, фишинг).** `/start login_…` и `/start pair_…`
  клеймят код без подтверждения. Злоумышленник генерит код у себя,
  шлёт жертве ссылку «бонус в боте» → жертва жмёт Start → лаунчер
  злоумышленника входит в аккаунт жертвы (с её подпиской).
- **B3.** `/api/tg/unbind` на `tg_*`-аккаунте (пароль случайный, email
  фиктивный) делает аккаунт недоступным навсегда; следующий вход через
  TG создаёт новый пустой аккаунт.
- **B4.** `/api/tg/bind` делает `DELETE … WHERE telegram_user_id = ? OR
  user_id = ?` — TG-id молча уходит с другого аккаунта. Если это был
  `tg_*`-аккаунт с подпиской — тот теряет вход, а новые платежи Tribute
  уходят на другой аккаунт.
- **B5.** Email-аккаунт с подпиской без привязки → «Войти через
  Telegram» создаёт дубль `tg_*` без подписки. Нет слияния.
- **B6.** `pair_codes.tiktok_sessionid` хранится открытым текстом и не
  стирается после `consumed` — в БД копятся живые TikTok-сессии.
- **B7.** `relay_admin_secret` вводится в лаунчере → любой стример
  регистрирует свой ключ на relay с любым `valid_until`.
- **B8.** Пропущенный webhook никак не восстанавливается: «Я оплатил —
  проверить» только перечитывает БД. Сверки с Tribute нет.
- **B9.** Ссылка бота для логина берётся из `TRIBUTE_BOT_URL` — вход
  зависит от биллингового конфига; нужен отдельный `TG_BOT_URL`
  (с фолбэком на старый).
- **B10.** Бот `/status` показывает `tg_123…@telegram.local` вместо
  ника; для TG-аккаунтов это мусор.
- **B11.** Оплата с *другого* TG-аккаунта (подарок, второй телефон)
  остаётся unmatched навсегда; у админа нет инструмента переназначить
  событие.

## 3. Целевые сценарии

### F1. Вход через Telegram (основной)
1. Лаунчер: `POST /api/auth/telegram-start {device_label}` →
   `{code, url}`; `device_label` = имя ПК + ОС (без HWID).
2. Пользователь жмёт Start → бот **не клеймит сразу**, а присылает
   сообщение «Войти в chlauncher на устройстве „…“? Код действует
   10 мин» с inline-кнопками «✅ Да, это я» / «❌ Нет».
3. «Да» → `POST /api/tg/login-claim` (как сейчас) + `confirmed=1`.
   «Нет» → код помечается отклонённым, лаунчер получает
   `status:'denied'`.
4. `/telegram-status` выдаёт JWT только для подтверждённого кода.
5. Аккаунта нет → создаём `tg_*` (как сейчас), ник из TG в профиль.

### F2. Вход по QR
Тот же поток подтверждения, что в F1 (страница `/pair/:code` →
бот `pair_<code>` → inline-подтверждение).

### F3. Привязка TikTok по QR
1. Залогиненный стример: Интеграции → «Привязать TikTok» →
   `open_tiktok_login` (встроенное окно TikTok web).
2. В окне вкладка «QR-код» → скан приложением TikTok на телефоне.
3. Перехват `sessionid` → `/api/auth/tiktok-login` с Bearer → привязка
   `auth_method='cookie'`, `tiktok_uid` (уже реализовано на сервере).
4. UI: явная кнопка/подсказка «войдите через QR в приложении TikTok»;
   окно сразу на странице QR-логина (проверить URL страницы).
5. Страница `/pair` с вставкой `sessionid` остаётся «продвинутым»
   вариантом; после `consumed` сессия стирается из `pair_codes` (B6).

### F4. Оплата
1. Т.к. вход через TG, `tg_bindings` есть всегда → кнопка тарифа сразу
   открывает ссылку Tribute (`tribute_links[plan]`).
2. Webhook → продление (как сейчас).
3. Уведомление: сервер кладёт запись в `tg_outbox`; бот поллит
   `GET /api/tg/outbox` (secret) раз в 5 с и шлёт «Оплата получена,
   подписка до …». Токен бота остаётся только у бота.
4. Лаунчер после открытия ссылки поллит `/api/account/subscription`
   раз в 10 с до 5 мин (или до смены статуса) + кнопка «Проверить».

### F5. Миграция email-аккаунтов
1. Вход email/паролем без TG → баннер «Привяжите Telegram — с <даты>
   вход только через Telegram» + кнопка (существующий link-code флоу).
2. **Слияние**, если TG уже привязан к `tg_*`-аккаунту: бот спрашивает
   «Этот Telegram уже входит в аккаунт X. Объединить с Y?»; при
   согласии — сервер переносит в целевой (email) аккаунт: `payments`,
   период подписки = max(end_a, end_b) + неиспользованные дни меньшего
   (правило уточнить, см. §8), `tiktok_bindings`, рефералов, тикеты;
   исходный `tg_*` помечается `merged_into`. Всё в одной транзакции +
   `admin_audit`.
3. После даты — `/login` для не-админов без TG → `TG_REQUIRED`
   (флаг конфигурации, не хардкод).

### F6. Отвязка и смена Telegram
- `tg_*`-аккаунт: отвязка запрещена (`TG_UNBIND_FORBIDDEN`).
- Смена TG: код из лаунчера → подтверждение в *старом* TG (если
  доступен) и в новом; иначе — через поддержку (админ-инструмент).
- `/api/tg/bind` больше не отнимает TG-id молча: если id привязан к
  другому аккаунту → `409 TG_ALREADY_BOUND` → F5 (слияние) (B4).

### F7. Регистрация ключа relay на сервере (вариант A внутри C)
- `POST /api/relay/register {stream_key}` — JWT + активная подписка,
  rate-limit; сервер сам вызывает `RELAY_URL/api/admin/register` с
  `RELAY_ADMIN_SECRET` из env, `valid_until = min(period_end, now+24h)`.
- Таблица `relay_keys (user_id PK, key_hash, registered_until,
  updated_at)` — один ключ на аккаунт; смена ключа → revoke старого на
  relay.
- Webhook `cancelled_subscription`/истечение — продление просто
  прекращается (relay сам отдаст 402 ≤ 24 ч).
- Лаунчер: `forwarder.rs::register_once` ходит в `apps/server`, поле
  admin-секрета убрать из UI (оставить только в dev-режиме для
  self-hosted relay).

### F8. Сверка платежей
- Исследовать API Tribute (`api.tribute.tg`, ключ уже есть в конфиге):
  можно ли получить подписки по `telegram_user_id`. **Не предполагать
  без документации.**
- Если можно — «Проверить оплату» дергает сверку для своего TG-id.
- В любом случае — админ-инструмент: список unmatched `billing_events`
  + «назначить пользователю» (B11).

## 7a. Roblox после релиза — без Studio, без ручного ключа

Studio нужен только разработчику. После публикации плейса:
зрители — обычный Roblox, стример — обычный Roblox-клиент + лаунчер.

```text
лаунчер «Играть» ─► POST /api/stream/ticket (JWT, подписка) ─► {ticket, 5 мин, одноразовый}
   └─► roblox://experiences/start?placeId=<P>&launchData={"t":"<ticket>"}
Roblox-сервер (облако): Player:GetJoinData().LaunchData → POST /api/stream/redeem
   {ticket, roblox_user_id} ─► привязка UserId ↔ аккаунт, ответ: room key
   → RoomService.StartStream автоматически (key уходит в TeleportData)
```

- **Почему тикет, а не сам ключ в URL.** Документация Roblox (Deep links):
  `launchData` ≤ 200 байт, «не передавайте конфиденциальное — данные
  видны в URL и могут быть подменены». Одноразовый тикет на 5 минут
  при утечке бесполезен; подделанный `launchData` просто не пройдёт
  redeem. `LaunchData` есть только при первом входе — дальше ключ
  едет в `TeleportData` (так RoomService уже делает).
- «Парсер ключа из URL» = этот механизм: стример ничего не вводит,
  ручной ввод ключа в меню остаётся запасным путём.
- **Ссылка для браузера/телефона**: то же через
  `https://www.roblox.com/games/start?placeId=<P>&launchData=…` —
  можно показать QR/кнопку «Скопировать ссылку входа» (тикет внутри).
- **Альтернатива на потом**: «Sign in with Roblox» (OAuth 2.0 Roblox,
  scope `openid`) в лаунчере — UserId стримера известен заранее, игра
  узнаёт стримера по UserId без ключа и тикета. Требует OAuth-приложения
  на create.roblox.com и секрета игрового сервера (Roblox Secrets /
  `HttpService:GetSecret`) — проверить доступность перед выбором.
- Публичный relay обязателен (Roblox-облако не видит ПК стримера) — см. 7b.
- Изменения в игре: `RelayClient.Redeem`, обработка `LaunchData` в
  `PlayerAdded`, баннер на 402 «подписка стримера истекла», ключ в
  заголовке `X-Stream-Key` вместо `?key=`, фиксы из отчёта по Roblox
  (перезапись `hostPlayer` зрителем, `wl-`-ключи, всплеск 60 с истории).
- Модель доступа сохраняется: стример с лаунчера — бесплатно (лицензия =
  подписка chlauncher), зрители — платный вход (Dev Product ~35 R$) или
  Backstage Pass. Дыры платного входа (`MonetizationService.RequestJoin`):
  покупка без проверки, что рума жива (`no_live_room` после оплаты →
  робуксы сгорают); вход в «первую попавшуюся» руму, а не к выбранному
  стримеру; при сбое телепорта после `PurchaseGranted` вход не
  возвращается. Нужно: выбор стримера в портале, проверка руммы и
  свободных мест (MAX_VIEWERS) ДО покупки, «оплаченный вход» как
  кредит в DataStore с повтором телепорта.

### Подсказка в лаунчере (текст для UI, иконка «?» у поля ключа)

> **Ключ стримера** — пропуск вашего эфира в Roblox-игру. Лаунчер
> отправляет по нему события (подарки, лайки, команды) на сервер, а
> сервер вашей румы в Roblox забирает их по этому же ключу.
> Ключ привязывается к одному Roblox-аккаунту при первом входе —
> передать его другу не получится, работает, пока активна подписка.
> Вводить его руками не нужно: «Играть» передаёт игре одноразовый
> пропуск сам. «Новый ключ» — если ключ утёк: старый перестанет
> работать, привязку к Roblox нужно будет пройти заново.

## 7b. Минимальная база: ничего не теряется при выходе/обновлении

Что где живёт сейчас и что теряется:

| Данные | Сейчас | Риск |
|---|---|---|
| Аккаунты, подписки, платежи | SQLite `apps/server` (WAL, миграции) | ок; бэкап — `tools/backup-db.sh` |
| Ключи relay, привязки UserId | `relay-state.json` рядом с кодом relay | теряется при передеплое папки |
| Очередь событий relay | память | рестарт relay = потеря событий в полёте + сброс курсора |
| Ключ стримера | `settings.json` лаунчера | переустановка/новый ПК = новый ключ, привязка к Roblox теряется |
| Очередь форварда (500) | память лаунчера | выход лаунчера = потеря неотправленного |
| Встроенный мост (dev) | память | рестарт = сброс claim/UserId (терпимо для dev) |

Предложение:

1. **Relay внутри `apps/server`** (роут-модуль `/api/stream/*`, тот же
   протокол — игре ничего менять, кроме URL). Сервер сам знает подписку
   → admin-секрет relay не нужен вообще, F7 упрощается до «сервер
   проверяет подписку при ingest/poll». Standalone `D:\roblox\relay`
   остаётся как референс/для self-host.
2. **Таблицы (миграция той же v15):**
   - `stream_keys (user_id PK, key_hash UNIQUE, roblox_user_id, created_at, rotated_at)` —
     ключ выдаёт **сервер**, лаунчер только кэширует → переустановка не
     ломает привязку.
   - `stream_tickets (ticket_hash PK, user_id, expires_at, used_at)` — 7a.
   - `stream_events (id AUTOINCREMENT, user_id, body, created_at)` —
     кольцевой буфер с TTL 60 с (чистка раз в 10 с, cap 500/юзер).
     `id` — монотонный курсор, переживает рестарт/деплой → игра не
     глохнет и не получает дубли.
   - `stream_rooms (user_id PK, job_id, claimed_at, last_poll_at)` — claim
     + «игра на связи» для UI.
3. **Лаунчер:** при выходе — дослать очередь форварда (≤ 2 с, затем
   бросить); перед первым запуском новой версии — копия
   `settings.json.bak-<version>` (держать 3 последних); тест на чтение
   старого settings.json уже есть — добавлять кейс на каждую миграцию.
4. **Обновления сервера:** миграции только аддитивные (как сейчас),
   бэкап БД перед деплоем в скрипте деплоя, healthcheck после.

## 7c. Права владельца: бесплатная подписка только у владельца

Сейчас: роль `admin` (выдаётся `tools/grant-admin.mjs`; `ADMIN_EMAILS`
в проде игнорируется) может всё, включая `grant-days`/`set-plan`/
`set-role`. `mock-pay` в проде выключен (и должен остаться выключенным).

Предложение — **владелец по Telegram ID**:

- env `OWNER_TG_IDS=<id>[,<id>]` на сервере. Владелец = аккаунт, чей
  `tg_bindings.telegram_user_id` в списке. Проверка на каждом запросе
  из БД + env, роль в JWT не доверяется. Выдать владельца через
  админку/БД нельзя — только правкой env на VPS.
- Иерархия: `owner` > `admin` (персонал: пользователи, HWID, поддержка,
  ревью игр) > `publisher` > `user`.
- **Только owner:** `grant-days`, `set-plan`, назначение `admin`,
  создание промокодов, выдача тестерских подписок.
- **Тестеры:** выдача с `provider='grant'`, обязательная причина, срок
  (по умолчанию 30 дн), опционально план `tester` (все фичи, без
  лимитов); список «Тестеры» в админке, всё в `admin_audit`.
- Бот: `/whoami` (показывает свой Telegram ID — чтобы вписать в env);
  владельцу — только чтение (`/testers`). Выдачу через бота не делать:
  если `TG_BIND_SECRET` утечёт, подделать `from.id` = выдать подписку
  кому угодно. Выдача — только из лаунчера под JWT владельца.
- Локально (dev) всё как сейчас: mock-pay + dev-режим.
